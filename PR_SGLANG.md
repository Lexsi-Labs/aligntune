# feat: SGLang rollout backend for TRL GRPO

## What this does

`rollout_backend="sglang"` was accepted by the config but never used: GRPO only branched on `"vllm"`, so it quietly fell back to plain `transformers` generation.
This PR makes it real.
With `rollout_backend="sglang"`, GRPO rollouts are generated by a running SGLang server, and the policy weights are pushed to that server after every optimizer step.

It also fixes a related bug: `create_rl_trainer(...)` never forwarded `rollout_backend` (or `vllm_tensor_parallel_size`) into `RLTrainingConfig`, so the Python API always ran `hf` whatever you passed.
Only YAML/CLI configs reached the field before.

## Design

Prior art I looked at before writing code:

| Candidate | What it does | Why not (or what was reused) |
|---|---|---|
| TRL PRs #2981, #3370, #3627 (closed, unmerged) | Patch `GRPOTrainer` with a `use_sglang` flag; sync via `update_weights_from_tensor` over HTTP | Needs TRL internals changed; tensor sync via HTTP sends CUDA IPC handles, which needs matching torch versions in both processes. Reviewers asked for weight-update timings that never arrived. |
| verl SGLang worker, radixark/miles | Colocated engine in the trainer process, `update_weights_from_tensor` / NCCL `update_weights_from_distributed` | Built for multi-node RL frameworks; needs SGLang importable in the trainer env. SGLang pins a different torch/transformers than aligntune. |
| SGLang LoRA hot-load (`/load_lora_adapter`) | Load a new adapter per step | Needs `--enable-lora` and LoRA flags on the server, LoRA kernels on every token, and only covers PEFT runs. |
| **SGLang server + `update_weights_from_disk` (chosen)** | Write weights to a file, server reloads them | SGLang's docs call it the simplest and safest refit path. It works for LoRA and full fine-tuning alike, and both sides only share HTTP and a file, so they can live in separate venvs. |

How it plugs in, with no TRL changes and no subclassing:

- TRL 1.7.1 already has a public `rollout_func` hook on `GRPOTrainer`.
  `SGLangRollout` (`src/aligntune/backends/trl/rl/rollout/sglang_rollout.py`) implements it, and `TRLGRPOTrainer.setup_trainer` passes it in only when `rollout_backend == "sglang"`.
  The `hf` and `vllm` paths are unchanged.
- **Generation.** Prompts are tokenized by TRL's own `_tokenize_prompts`, so the chat template and tokens match the `hf` path exactly.
  TRL repeats each prompt `num_generations` times back to back.
  `SGLangRollout` collapses each group into one prompt sent with `n=num_generations`.
  SGLang then prefills the prompt once and shares its KV cache across the group through RadixAttention.
  Measured: with `n`, SGLang reported 1216 of 1216 prompt tokens cached on the repeated samples, against 0 when the same prompts were sent as separate duplicates.
  Sampling settings (`temperature`, `top_p`, `top_k`, `min_p`, `repetition_penalty`, `max_completion_length`, EOS stop) are mapped from the trainer.
  The EOS token stays in `output_ids`, as it does on the `hf` path.
- **Weight sync.** Before the first rollout, and after every optimizer step after that, the policy is exported to `<sync_dir>/model.safetensors` (default: a temp dir in `/dev/shm`), then `POST /update_weights_from_disk` is called, which also flushes the prefix cache.
  LoRA deltas (`get_delta_weight`) are added to fp32 copies of the base weights.
  The trainer's model is never merged and unmerged in place: doing that every step would pile bf16 rounding error into the frozen base weights.
  Tied embeddings are written once.
  DeepSpeed ZeRO-3 params are gathered through TRL's `_dist.gather_params`, and only the main process writes the file and calls the server.
- **Failure is loud.** The constructor calls `/model_info`, so an unreachable server raises `ConnectionError` during trainer setup, with a message that says how to start SGLang or switch to `hf`.
  Any non-200 response or `success: false` on a weight update raises.
  Nothing falls back.
- **Metrics.** `rollout/sglang_generate_s`, `rollout/sglang_tokens_per_s` and `rollout/sglang_sync_s` show up next to TRL's own metrics.

## Usage

```bash
# SGLang can live in its own venv; it only needs HTTP and the sync dir.
python -m sglang.launch_server --model-path Qwen/Qwen2.5-0.5B-Instruct \
    --port 30000 --mem-fraction-static 0.25 --skip-tokenizer-init
```

```python
trainer = create_rl_trainer(
    model_name="Qwen/Qwen2.5-0.5B-Instruct",
    algorithm="grpo", backend="trl",
    rollout_backend="sglang",
    sglang_server_url="http://127.0.0.1:30000",   # default http://127.0.0.1:30000
    # sglang_sync_dir="/dev/shm/my-run",          # optional; must be readable by the server
    ...
)
```

`--skip-tokenizer-init` is optional but recommended, because the trainer sends and receives token ids and the server never has to detokenize.

CLI: `--rollout-backend sglang --sglang-url http://127.0.0.1:30000`.
YAML: `train.rollout_backend: sglang`, `train.sglang_server_url: ...`.

A full GSM8K example with a timing harness is in `examples/trl_grpo_sglang_gsm8k.py`.

## Tests

- `tests/test_sglang_rollout.py` (CPU, 14 tests).
  These run against an in-process fake SGLang HTTP server and cover:
  - an unreachable server, HTTP errors and failed weight updates, all of which raise;
  - the output contract for TRL's `rollout_func`;
  - GRPO groups sent once with `n`, and uneven groups falling back to one sample per prompt;
  - the sampling-parameter mapping;
  - one sync per optimizer step (none during gradient accumulation);
  - the exported weights for full models, tied embeddings and PEFT (base names, LoRA delta folded in, model not mutated);
  - FSDP being rejected.
- `tests/test_sglang_rollout_integration.py` (GPU + live server, skipped unless `SGLANG_URL` is set).
  It applies a random LoRA to Qwen2.5-0.5B, syncs it, and compares per-token logprobs of a fixed continuation from SGLang against the trainer's policy.
  Result: the policy moves logprobs by 0.517 nats/token, and after sync SGLang is within 0.063 nats/token of the policy.
  That matches the 0.057 bf16 kernel noise floor between SGLang and transformers at the base weights.
- Existing `tests/test_vllm_rollout_config.py` and `tests/test_vllm_rollout.py` still pass.

## Limitations

- The server has to run on the same host as the trainer, because the weights go through the filesystem.
  A remote or multi-node rollout fleet would need `update_weights_from_distributed` (NCCL); the hook point is `SGLangRollout.sync_weights`.
- Each sync writes the full model.
  For 0.5B that takes about 1 s per step (see benchmarks).
  For 7B+ LoRA runs, adapter hot-loading (`/load_lora_adapter`) would be cheaper and is a natural follow-up.
- No importance-sampling correction for the mismatch between SGLang and the trainer (TRL only does that for vLLM).
  `logprobs` is returned as `None`, like the `hf` path.
- Not supported yet: multimodal prompts, FSDP and DoRA (each raises `NotImplementedError`).
- Only `TRLGRPOTrainer` and the variants that inherit its `setup_trainer` (GSPO, DAPO, Dr. GRPO) are wired.
  GBMPO, PACE, counterfactual GRPO and the Unsloth backend build their own trainers and ignore `rollout_backend`, as they already do for `vllm`.
- Tested with SGLang 0.5.22 (`/model_info` endpoint), TRL 1.7.1 and transformers 5.19.
  On an RTX 5070 Ti (sm_120), the server needed `--attention-backend triton --sampling-backend pytorch` because flashinfer's JIT failed to build against the pip CUDA 13 toolkit.
  That is an environment issue, not part of this change.
