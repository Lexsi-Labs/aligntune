# feat: SGLang rollout backend for TRL GRPO

## What and why

`rollout_backend="sglang"` was accepted by the config but never used.
GRPO only branched on `"vllm"`, so it quietly fell back to plain `transformers` generation.
This PR makes it real.
With `rollout_backend="sglang"`, GRPO rollouts are generated by a running SGLang server, and the policy is pushed to that server after every optimizer step.
On a 0.5B GSM8K run this cuts rollout time by about 9x and GRPO step time by about 2.5x (see Benchmarks).

It also fixes two related bugs:

- `create_rl_trainer(...)` never forwarded `rollout_backend` (or `vllm_tensor_parallel_size`) into `RLTrainingConfig`, so the Python API always ran `hf` whatever you passed.
  Only YAML/CLI configs reached the field before.
- Trainers that do not implement a rollout backend silently ignored it.
  `rollout_backend="sglang"` now raises a `ValueError` on every trainer that cannot honour it, including the whole Unsloth backend, PACE and counterfactual GRPO, instead of quietly generating with `transformers`.

## Design

Prior art I looked at before writing code:

| Candidate | What it does | Why not (or what was reused) |
|---|---|---|
| TRL PRs #2981, #3370, #3627 (closed, unmerged) | Patch `GRPOTrainer` with a `use_sglang` flag; sync via `update_weights_from_tensor` over HTTP | Needs TRL internals changed; tensor sync over HTTP sends CUDA IPC handles, which needs matching torch versions in both processes. |
| verl SGLang worker, radixark/miles | Colocated engine in the trainer process, `update_weights_from_tensor` / NCCL `update_weights_from_distributed` | Built for multi-node RL frameworks; needs SGLang importable in the trainer env, and SGLang pins a different torch/transformers than aligntune. |
| **SGLang server + LoRA hot-load / `update_weights_from_disk` (chosen)** | Write the adapter (or the weights) to a RAM-backed dir, server loads them | Both sides only share HTTP and a directory, so SGLang and aligntune can live in separate venvs with different torch versions. |

How it plugs in, with no TRL changes and no subclassing:

- TRL 1.7.1 has a public `rollout_func` hook on `GRPOTrainer`.
  `SGLangRollout` (`src/aligntune/backends/trl/rl/rollout/sglang_rollout.py`) implements it, and `TRLGRPOTrainer.setup_trainer` passes it in only when `rollout_backend == "sglang"`.
  GSPO, DAPO, Dr. GRPO and GBMPO inherit that `setup_trainer`, so they get it too.
  The `hf` and `vllm` paths are unchanged.
- **Generation.** Prompts are tokenized by TRL's own `_tokenize_prompts`, so the chat template and tokens match the `hf` path exactly.
  TRL repeats each prompt `num_generations` times back to back.
  With full-weight sync, each group is sent once with `n=num_generations`, so SGLang prefills the prompt once and shares its KV cache across the group (RadixAttention).
  With adapter sync, the group's prompt is prefilled once (`max_new_tokens=0`) and the samples are then sent as duplicates that hit the prefix cache.
  This avoids an SGLang 0.5.10 bug: an adapter used by an `n > 1` request is acquired once per prompt but released once per sample, so its reference count never returns to zero and `/unload_lora_adapter` hangs forever (fixed by 0.5.22).
  Sampling settings (`temperature`, `top_p`, `top_k`, `min_p`, `repetition_penalty`, `max_completion_length`, EOS stop) are mapped from the trainer.
  The EOS token stays in `output_ids`, as it does on the `hf` path.
- **Weight sync**, before the first rollout and after every optimizer step.
  The mode is chosen from the server's own `/server_info` (`enable_lora`), not from its version:
  - **Adapter sync** (server started with `--enable-lora`, PEFT LoRA policy).
    The adapter is saved to one of two alternating dirs, loaded under a new name (`/load_lora_adapter`), and the previous version is unloaded.
    Base weights never move, so only the adapter (tens of MB for 0.5B r=16, a few hundred MB for 8B) is written per step.
    The first sync checks that the server serves the policy's base model and raises if not.
    LoRA variants SGLang cannot apply (rsLoRA, DoRA, `modules_to_save`) raise `NotImplementedError` up front.
  - **Full sync** (any other server, or a full fine-tune).
    Weights are streamed one module at a time into sharded `model-XXXXX.safetensors` files of at most 1 GiB, then `POST /update_weights_from_disk` reloads them.
    LoRA deltas (`get_delta_weight`) are added to fp32 copies of the base weights one module at a time, so host RAM stays at about one shard.
    The trainer's model is never merged and unmerged in place, which would pile bf16 rounding error into the frozen base weights.
  - DeepSpeed ZeRO-3 params are gathered through TRL's `_dist.gather_params`; only the main process writes files and calls the server.
  - The default sync dir is a fresh temp dir in `/dev/shm`, removed when the rollout object is collected or the process exits.
- **Failure is loud. Nothing falls back.**
  The constructor calls `/model_info`, so an unreachable server raises `ConnectionError` during trainer setup, with a message that says how to start SGLang or switch to `hf`.
  Any non-200 response, `success: false` on a weight update, a wrong output count or a request that times out raises.
  FSDP and multimodal prompts raise `NotImplementedError`.
- **Metrics.** `rollout/sglang_generate_s`, `rollout/sglang_tokens_per_s` and `rollout/sglang_sync_s` show up next to TRL's own metrics.

## Supported versions

- SGLang **0.5.10.post1 to 0.5.22**, both tested end to end.
  Every endpoint used (`/model_info`, `/server_info`, `/generate`, `/update_weights_from_disk`, `/load_lora_adapter`, `/unload_lora_adapter`) exists in both, and behaviour is selected by feature detection (`/server_info`), never by version string.
- TRL 1.7.1 (`rollout_func`), transformers 5.x, peft 0.21.
- SGLang can live in its own venv with its own torch (tested: SGLang 0.5.10.post1 on torch 2.9.1+cu128 next to an aligntune venv on a different torch).

## Usage

```bash
# SGLang can live in its own venv; it only needs HTTP and the sync dir.
# Adapter sync (recommended for LoRA runs): add the LoRA flags matching your PEFT config.
python -m sglang.launch_server --model-path Qwen/Qwen2.5-0.5B-Instruct \
    --host 127.0.0.1 --port 30000 --mem-fraction-static 0.25 \
    --enable-lora --max-lora-rank 16 --lora-target-modules all \
    --skip-tokenizer-init --sleep-on-idle
```

```python
trainer = create_rl_trainer(
    model_name="Qwen/Qwen2.5-0.5B-Instruct",
    algorithm="grpo", backend="trl",
    rollout_backend="sglang",
    sglang_server_url="http://127.0.0.1:30000",   # default
    # sglang_sync_dir="/dev/shm/my-run",          # optional; must be readable by the server
    ...
)
```

Without the `--enable-lora` flags the same run uses full sync.
`--skip-tokenizer-init` and `--sleep-on-idle` are optional but recommended: the trainer sends and receives token ids, and an idle scheduler that sleeps leaves CPU for the training phase.

CLI: `--rollout-backend sglang --sglang-url http://127.0.0.1:30000`.
YAML: `train.rollout_backend: sglang`, `train.sglang_server_url: ...`, optional `train.sglang_sync_dir: ...`.

A full GSM8K example with a timing harness is in `examples/trl_grpo_sglang_gsm8k.py`, and a rollout-only A/B benchmark is in `examples/bench_sglang_rollout.py`.

## Benchmarks

Setup: one RTX 5070 Ti (16 GB), Qwen2.5-0.5B-Instruct, GSM8K, LoRA r=16 on all linear layers, 8 prompts x 8 samples per step, up to 256 new tokens, temperature 1.0.
SGLang ran on the same GPU with `--mem-fraction-static 0.25`.
The trainer process was capped at 2 CPUs by a cgroup, so every run waited for a quiet window and recorded the cgroup's `nr_throttled` count; the throttled share is in the last column.

**Rollout only** (`examples/bench_sglang_rollout.py`, HF `generate` and SGLang interleaved on the same prompts, median of 6 rounds after a warmup):

| SGLang | Sync mode | HF generate | SGLang | Speedup | Sync per step | Peak trainer RSS growth during sync | Throttled periods |
|---|---|---|---|---|---|---|---|
| 0.5.22 | full | 6.78 s (1623 tok/s) | 0.70 s (14949 tok/s) | 9.6x | 0.74 s | not measured | 38 / 1057 |
| 0.5.10.post1 | full | 6.95 s (1629 tok/s) | 0.70 s (14180 tok/s) | 9.9x | 0.73 s | 262 MiB | n/a (1) |
| 0.5.10.post1 | adapter | 6.64 s (1748 tok/s) | 0.87 s (10683 tok/s) | 7.6x | 1.13 s | 35 MiB first sync, 0-2 MiB after | 84 / 982 |

(1) That window also covered a stuck server shutdown, so its counter is not meaningful; the rounds themselves ran in a quiet window.

In adapter mode, 99% of prompt tokens were served from the prefix cache (for example 6664 of 6728), so prefilling each group once and then sending duplicates costs about the same as `n` sampling.
LoRA kernels make adapter-mode decoding somewhat slower than a merged model.
At 0.5B, full sync is faster than adapter sync because the whole model is only 1 GB.
For larger models, full sync writes the whole model every step, while adapter sync writes only the adapter.

**30-step GRPO end to end** (`examples/trl_grpo_sglang_gsm8k.py`, median over steps 2-30):

| Rollout backend | Step | Rollout (incl. sync) | Rollout tokens/s | Reward, first 10 -> last 10 steps | Throttled periods |
|---|---|---|---|---|---|
| hf | 9.8 s | 7.4 s | 2221 | 0.205 -> 0.347 | 30 / 3163 |
| sglang 0.5.22, full sync | 3.9 s | 1.5 s (gen 0.77 s + sync 0.74 s) | 9122 | 0.208 -> 0.319 | 94 / 1725 |
| sglang 0.5.10.post1, adapter sync | 4.3 s | 1.9 s (gen 0.97 s + sync 0.88 s) | 7152 | 0.277 -> 0.367 | 37 / 1691 |

That is about a 2.3x to 2.5x faster GRPO step. The remaining time is the policy's forward and backward pass, which this PR does not change.
Over 60 steps (run while the host was busy, so timings are not comparable), reward per 10-step bin went 0.217 -> 0.334 -> 0.398 -> 0.377 -> 0.320 -> 0.366 with SGLang and 0.205 -> 0.319 -> 0.392 -> 0.377 -> 0.364 -> 0.383 with HF.
The learning curves match, as expected, since both backends sample from the same policy.

## Test plan and results

- `tests/test_sglang_rollout.py`: 26 CPU tests against an in-process fake SGLang server, all passing.
  They cover:
  - an unreachable server, HTTP errors, failed weight updates and a stuck server, all of which raise;
  - the output contract for TRL's `rollout_func`;
  - GRPO groups sent once with `n`, uneven groups, and adapter mode prefilling groups without `n`;
  - the sampling-parameter mapping;
  - one sync per optimizer step (none during gradient accumulation);
  - full sync: exported weights for full models, tied embeddings and PEFT (base names, LoRA delta folded in, model not mutated), sharding, and sync-dir cleanup;
  - adapter sync: hot-load of a new version and unload of the old one, full-model policies on a LoRA server, base-model mismatch, and rsLoRA/DoRA/`modules_to_save` rejected;
  - FSDP rejected, and every trainer without SGLang support (Unsloth, PACE, ...) raising instead of silently using `hf`.
- `tests/test_sglang_rollout_integration.py` (GPU + live server, skipped unless `SGLANG_URL` is set).
  It applies a random LoRA to Qwen2.5-0.5B, syncs it, and compares per-token logprobs of a fixed continuation from SGLang against the trainer's policy.
  The random LoRA moves logprobs by about 0.52 nats/token; after sync, SGLang must agree with the policy to within the bf16 kernel noise floor between SGLang and transformers at the base weights.

  | SGLang | Sync mode | SGLang vs policy after sync | Noise floor (base weights) |
  |---|---|---|---|
  | 0.5.22 | full | 0.063 nats/token | 0.057 |
  | 0.5.10.post1 | full | 0.049 | 0.052 |
  | 0.5.10.post1 | adapter | 0.038 | 0.052 |
  | 0.5.10.post1 (Qwen3-0.6B) | adapter | 0.032 | 0.060 |

- End-to-end GRPO runs on GSM8K (above) with reward rising over 30 and 60 steps on both backends.
- Existing `tests/test_vllm_rollout_config.py` and `tests/test_vllm_rollout.py` still pass; `black` and `flake8 --max-line-length 100` are clean on the new files.

## Limitations

- The server has to run on the same host as the trainer, because the adapter or weights go through the filesystem.
  A remote or multi-node rollout fleet would need `update_weights_from_distributed` (NCCL); the hook point is `SGLangRollout.sync_weights`.
- No importance-sampling correction for the mismatch between SGLang and the trainer (TRL only does that for vLLM).
  `logprobs` is returned as `None`, like the `hf` path.
- Adapter sync supports plain LoRA only, since SGLang scales adapters by `lora_alpha / r`.
  rsLoRA, DoRA and `modules_to_save` raise; start the server without `--enable-lora` to use full sync for them.
- Not supported yet (each raises): multimodal prompts, FSDP, the Unsloth backend, PACE and counterfactual GRPO.
  Unsloth support needs its own `rollout_func` wiring and is a natural follow-up.
- With full sync, a large model is written to `/dev/shm` every step (about 1 s for 0.5B); prefer adapter sync for LoRA runs.
- On an RTX 5070 Ti (sm_120), the server needed `--attention-backend triton --sampling-backend pytorch` because flashinfer's JIT failed to build against the pip CUDA 13 toolkit.
  That is an environment issue, not part of this change.

## Notes for reviewers: SGLang 0.5.10 LoRA ref-count bug

Found while testing adapter sync on 0.5.10.post1; 0.5.22 behaves correctly.
In `TokenizerManager`, a `/generate` request with `lora_path` and `sampling_params.n > 1` acquires the adapter once per prompt in `_resolve_lora_path`, but `_handle_batch_request` expands it into one prefix-cache request plus `n` sample requests, and each finished request releases the adapter.
The adapter's `ConcurrentCounter` goes negative, `wait_for_zero()` never returns, and `/unload_lora_adapter` hangs forever, blocking every later load/unload behind it.
Minimal repro against a server started with `--enable-lora --max-lora-rank 16 --lora-target-modules all`:

```bash
U=127.0.0.1:30000; J="content-type: application/json"
curl -s $U/load_lora_adapter -H "$J" -d '{"lora_name":"a","lora_path":"/path/to/peft_adapter"}'
curl -s $U/generate -H "$J" -d '{"input_ids":[[1,2,3]],"lora_path":"a","sampling_params":{"max_new_tokens":4,"n":4}}'
curl -s -m 20 $U/unload_lora_adapter -H "$J" -d '{"lora_name":"a"}'   # 0.5.10.post1: times out; 0.5.22: 200
```

With `n` omitted (or prompts duplicated), the same unload returns 200 on both versions.
This PR works around it on every version by not using `n` in adapter mode (see Design).
I have not filed this upstream with SGLang; the repro above is ready to file if useful.
